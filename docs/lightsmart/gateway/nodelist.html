获取子设备节点列表 (hapi) ​

网关固件拉取需要连接的 BLE Mesh 子设备列表（本篇为固件契约接口，由 hapi 实现）：

POST {base_url}module/module/nodelist
Content-Type: application/json
X-Beancomm-Timestamp: <unix 秒>
X-Beancomm-ModuleCode: <模块编码>
X-Beancomm-HardwareId: <网关SN>
X-Beancomm-Signature: <md5 签名>
  • {base_url} 由初启引导接口 certificate 下发（实测返回 http://hotel.chintiot.com/hapi/），故线上地址为 https://hotel.chintiot.com/hapi/module/module/nodelist。
  • 固件二进制内置默认 http://hotel.beancomm.net/api/v5/ 仅作初启兜底（该地址已下线，nginx 404），运行时以 certificate 下发的 base_url 为准。
  • 请求方法必须为 POST（GET 会因 express.text 不解析 body 而导致签名校验失败）。
  • 鉴权为 hapi 网关中间件：4 个 X-Beancomm-* 头 + 签名校验（utils/auth.js）。

响应:

json
{
  "errno": 0,
  "errmsg": "SUCCESS",
  "data": {
    "node": [
      ["AABBCCDDEEFF", 430, 841, 12, 2, 0]
    ],
    "meshkey": "u1a2b3c4d5e6f7g8",
    "dbg": { "hotel_id": 0, "getCipherKey": false },
    "qr_code": ""
  }
}
键位置类型说明
nodedataarray子设备行数组，见下
meshkeydatastring私有 Mesh 私钥（小写 k），取自 sh_room_tb.private_mesh_info.privateKey；房间未配网时可为 ""
dbgdataobject调试信息，键条件出现（先 hotel_id，结束时补 getCipherKey，必要时再补 bleLockProjectId）
qr_codedatastring默认 ""；屏类设备（pid=210 + 屏配置）时返回控制页二维码链接
lockKeydatastring可选：存在 pid=530 门锁且酒店配置了 bleLockProjectId 时返回

node 数组元素（6 段，顺序固定）:

[mac, naddr, pid, dev_type, subNum, dlocId]

下标字段类型说明
0macstring设备 MAC（12 位 hex）
1naddrnumberMesh 短地址（缺省 0）
2pidnumber产品 ID（缺省 0）
3dev_typenumber设备类型码（deviceTypeArr 索引；未知名 = -1）
4subNumnumber子设备序号
5dlocIdnumber点位 ID（缺省 0）

网关固件只读取下标 0–4，第 6 段（dlocId）被忽略；网关自身（gateway / private_mesh_gateway / embedded4）不入 node 列表。

依据 service-lightsmart-hapi/src/service/beancomm.js:720-782、controller/module/module.js:279、route/module/module.js:10、common/device.js:5、utils/auth.js:127、utils/global.js:41。

附：ztmp 备用实现（固件不使用） ​

ztmp 侧另有一套同形接口（第二实现）：

POST https://ztmp.chintiot.com/ztmp/module/module/nodelist
X-Beancomm-HardwareId: <网关SN>
json
{
  "errno": 0,
  "errmsg": "SUCCESS",
  "data": {
    "node": [
      ["AABBCCDDEEFF", 12345, 841, 12, 1]
    ],
    "meshKey": "u1a2b3c4d5e6f7g8"
  },
  "meshKey": "1111",
  "lockKey": "2222"
}

node 数组元素：[mac, naddr, pid, type, subType]（5 段）

鉴权：仅读取 X-Beancomm-HardwareId 作为 SN，不校验时间戳/签名。

与 hapi 的差异 ​

维度hapi（固件契约）ztmp（备用实现）
私钥键名data.meshkey（小写）data.meshKey（驼峰）
node 段数6 段5 段（无第 6 段 dlocId）
node[4] 源字段subNumdevice.subType（实测数值与 subNum 不同）
顶层多余键无硬编码常量 meshKey:'1111'、lockKey:'2222'（位于 data 之外）
信封 / node[0..3]{errno,errmsg,data} / mac·naddr·pid·类型码同（下标 0–3 实测对齐）
鉴权4 个 X-Beancomm-* 头 + 签名校验仅 HardwareId

休眠不一致项（非缺陷）：ztmp 版当前无调用方——app-lightsmart-uniapp、app-lightsmart-ztutil、固件、hapi 侧对 nodelist / module/module 均 0 命中。其私钥键名为 data.meshKey（驼峰），与 hapi/固件读取的 meshkey（小写）不一致；固件 cJSON 取键大小写敏感，故属休眠不一致，将来启用前必须先确认消费端键名。

依据 service-lightsmart-ztmp/src/http/ztmp.ts:4-43；键名/段数/取数实测见 device-lightsmart-BCW018X/取证_A5_nodelist形态.md。

修订记录 ​

  • 2026-09-26（A5 裁定）：本篇位于「网关固件接口」栏目，原稿却整篇记为 ztmp 形态（错端点 ztmp.chintiot.com + 错键名 meshKey）；现改为主记 hapi（data.meshkey 小写、node 6 段、X-Beancomm-* 鉴权），ztmp 版降为附注小节并客观标注「固件不使用 · 当前无调用方 · 键名与 hapi 不一致（休眠不一致项）」。
    • 依据一：固件 URL 拼装为 base_url + "module/module/nodelist"（反编译串 0x3C0B2BD0，无 /ztmp 前缀）。
    • 依据二：固件发送的 6 个 X-Beancomm-* 头与 hapi utils/auth.js:127 逐项对应（ztmp 只校验 HardwareId）。
    • 依据三：线上实测 POST tiny.beancomm.net/api/module/module/certificate → {"base_url":"http://hotel.chintiot.com/hapi/"}，随后 POST hotel.chintiot.com/hapi/module/module/nodelist → 200 {"node":[],"meshkey":"","dbg":{},"qr_code":""}（键名即 hapi 形态）。
    • 依据四：固件解析器在 data 内取键，私钥键写死小写 meshkey（cJSON_GetObjectItem(data,"meshkey")）。
    • 说明：ztmp 版仅为休眠不一致，不构成当前故障；原「与 ztmp 代码一致、无需改」的结论已按本条取证推翻。
